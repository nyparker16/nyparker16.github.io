Research · UBC Systopia Lab · May 2026–present

Verifying concurrent programs with timestamped atomics

Concurrent code has to be correct under every possible interleaving of its threads. I'm building a way to check that quickly by giving every atomic operation a timestamp.

Soo-Ho Park, Finn Hackett, Yuanhao Wei and Ivan Beschastnikh · Undergraduate Student Research Award (USRA), Summer 2026

The problem

Atomic instructions like load, store and compare-and-swap (CAS) are indivisible on their own. But a data structure built from them, such as a lock-free stack, is only correct if every run behaves like some valid one-at-a-time ordering of its operations. This property is called linearizability.

Checking it usually means searching for such an ordering. With n overlapping operations there are up to n! orderings to try, so checking slows down sharply as threads are added.

The approach

I implemented TimestampedAtomic in C++, a wrapper that stamps each load, store and CAS with a value from a shared clock. The stamp marks the operation's linearization point, so a checker can sort a trace by timestamp instead of searching all orderings.

  • V0, linked list: every store adds a node, so a load can walk back to the value that was current when it read the clock. Threads help finish each other's stamps, so stamping is wait-free.
  • V1, single node: keeps only the latest value and frees old nodes safely with epoch-based reclamation.

Proof of correctness

I wrote a formal proof for V0 that contributes to a research paper. In six lemmas and four theorems, it shows that every interleaving of load, store and CAS is linearizable, and that sorting by timestamp always gives a valid linearization. The repository also includes a TLA+ model of the algorithm.

Code, TLA+ model and full proof on GitHub ↗

Results

Tested on a Treiber stack, a classic lock-free stack, with 1 to 5 threads. Each point is the mean of 10 runs.

Next steps

  • Prove V1 correct
  • Build V2, which removes the extra pointer hop to reach the current value
  • Timestamp more instructions, such as fetch_add and fetch_sub
  • Handle linearization points that aren't fixed in advance

Operating system · Jul 2026–present

SkyOS

In progress

A freestanding x86 kernel written in C++. It runs with no operating system or standard library underneath, and boots from a floppy image through GRUB.

Built
Solo
Toolchain
MSVC, GRUB 0.95, QEMU
Kernel size
25 KB

Work in progress: this build boots and prints to the screen. More features are being added.

What it does

GRUB loads the kernel into memory at 1 MiB and jumps to it. From there SkyOS owns the machine: no C runtime, no system calls, nothing to fall back on. Right now it boots and writes to the screen, the base for everything that comes next.

How it works

  • Written in C++ with x86 assembly, built by Microsoft's compiler into a Windows-style PE executable.
  • The default C runtime is switched off, so the binary runs on bare hardware.
  • The memory layout and alignment are set by hand so GRUB can load the file.
  • Packaged into a bootable disk image and run under QEMU.

The tricky part

GRUB doesn't understand Windows executables. The kernel carries a Multiboot header whose "a.out kludge" flag tells GRUB exactly where to load it and where to start.

magic 0x1BADB002 flags 0x00010003 → bit 16 set: use the addresses below load_addr 0x00100000 entry 0x00100420

Web app · Aug 2025

Vancouver Recreation Scheduler

Finds City of Vancouver recreation programs by age, day and community centre, then lays the ones you pick onto a weekly calendar. More than 6,000 listings live in an Azure SQL database behind a Flask API.

Team
3 people
My part
Scraper, data pipeline and search API
Database
Azure SQL · 6,000+ listings

Demo recorded against a local copy of the database with sample activities. The real app reads from Azure SQL.

What it does

Parents juggling several kids' activities can filter hundreds of city programs at once instead of clicking through listings one by one, then see the whole week at a glance.

How it works

  • A headless Selenium scraper works through the city's infinite-scroll search and collects every listing.
  • Dates, times and age ranges are normalized with regex and loaded into an activities table in Azure SQL Database, with ages as numbers of years and proper DATE and TIME columns so they can be compared.
  • A Flask REST API queries the database through pyodbc with parameterized SQL, so age overlap, weekday and location filters run in the database. The login comes from environment variables, not the code.
  • The React calendar assigns overlapping classes to separate lanes.

The tricky part

The city writes ages and times as free text, so the scraper turns them into numbers.

"Age at least 6y but less than 9y" → min 6.0, max 9.0 "18 m +" → min 1.5, max 150 "Sat 11:30 AM - Noon" → Sat 11:30–12:00

Mobile app · Oct 2025

Cree Learner

Hackathon project

Built in 24 hours with a team at the SFU StormHacks 2025 hackathon. A mobile app for learning Plains Cree vocabulary: tap syllabics to hear them and memorize words with audio pronunciation.

Event
SFU StormHacks 2025, 24 hours
My part
Flask API and Azure database
Platforms
iOS and Android

Demo recorded without the Azure services, so it uses sample words.

What it does

Cree is written in syllabics, where each symbol's shape and rotation encode a consonant and vowel. The app turns the chart into something you can tap and hear.

ᐊ ᐃ ᐅ ᐁ

How it works

  • React Native app in TypeScript with tab navigation.
  • Vocabulary lives in a words table in Azure SQL Database: each word's Cree spelling, pronunciation guide, meaning and a link to its recording.
  • A Flask REST API pulls a word from the database for the app, so new words can be added without releasing a new version.
  • The pronunciation recordings are stored as files in Azure Blob Storage.

My part

I built the backend: the Flask API the app calls for each word, the Azure SQL table of word entries, and the Blob Storage container that holds the pronunciation recordings.

Course project · CPSC 1045, Langara College · Fall 2022

Infection Simulator

A disease-spread simulation in the browser. Set the population, the share infected and the number of time steps, then watch the infection spread while immune carriers race to a lab to create a vaccine.

Built with
JavaScript and SVG
Inputs
People, % infected, time steps
Runs in
Any browser, no libraries

What it does

At the end of the run it counts survivors against the infected and declares a winner. More time steps give the vaccine longer to spread, so survivors are more likely to win.

How it works

  • Each step, every person takes a small random step.
  • Every pair closer than 8 pixels counts as a contact, and infection passes between them.
  • Immune carriers, 2% of the population, walk straight to the lab. When half arrive, the vaccine is created.
  • Vaccinated people leave the hospital and vaccinate everyone they touch.
